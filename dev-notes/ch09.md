**Claude 关键产出**

- 独立 builder 读完 spec + 现有代码，提了 7 个会逼人猜错的问题，按重要性排序：
  1. 审核通过与向量化的顺序/重试：先置「通过」再向量化失败会卡死；`vectorize_pending` 是表级，不是单条。
  2. 重排不可用时 `result.reranked=False`，分数是 RRF 量级，机械闸会误杀所有知识问题。
  3. 谁提供 Langfuse：验收 1 需要运行中的自部署实例，仓库只有 MySQL compose。
  4. `tool_intent_gate` 直达 Agent、pending refund resume 跳过 `classify_intent`，这些 trace 没有意图标签。
  5. `top1/top2/gap` 若取 `prompt_order` 的展示序，`ordered[1]` 实际是第三高分。
  6. 飞轮并发：同一问题两行并发处理会重复插 `review_queue`，`occurrence_count` 读改写丢增量。
  7. 校准口径与生产不一致：ch04 脚本用 LLM QueryRewriter，生产知识路用 `NoOpQueryRewriter`。
- 处理结果（全部写进 spec §10）：
  1. 先插 chunk（`source_doc=review_queue:{id}`）→ 只向量化该 chunk → 成功后才置「通过」；失败保持「待审」可重试；同 source_doc 幂等。
  2. `reranked=False` 跳过机械闸，只跑 EvidenceChecker，trace 记 `confidence_skipped`。
  3. 仓库加 `deploy/langfuse/docker-compose.yml` + `.env.example`；也支持现成实例。
  4. runtime 在拿到最终 state 后 `finish_turn_trace(values)`，不在节点里更新；覆盖 gate/resume/interrupt。
  5. 信号从 `result.hits` 按 score 降序取，不用展示序。
  6. `FlywheelService` 单 worker + `asyncio.Queue` 串行；跨进程竞争记为已知限制。
  7. 校准用 `NoOpQueryRewriter` + `min_score=settings.rerank_min_score` + 无 content_type；退款路沿用同阈值并记 `confidence_route="refund"`。

**拒绝 / 纠偏**

- 没有把 7 条都甩给用户：6 条能由既有约束和代码推出，直接裁决并写进 spec；只有「Langfuse 由谁提供」需要用户确认实例现状。

## 2026-10-29 · Langfuse 部署形态改判（Cloud 默认）

**用户关键原话**

- 「langfuse目前是什么情况，我刚接触，我看还要什么服务器地址，你怎么配的」
- 「我没太理解意思，那我还需要专门花钱买一个云服务器吗？」
- 「云端免费额度多少？我这里教的是建议云端，避免本地负担太重」
- 「课程用的演示数据」
- 「那就走云端吧，负担小」

**Claude 关键产出**

- 澄清「服务器地址」是 `LANGFUSE_BASE_URL`（Langfuse 服务对 app 进程可见的地址），不是 LLM 地址；自部署时为 `http://localhost:3000`，Cloud 时为 `https://cloud.langfuse.com`（US 区 `https://us.cloud.langfuse.com`）。
- 核对 Langfuse Cloud 当前 Hobby 免费档：**50k units/月、30 天数据访问、2 用户、无需信用卡**；`units = traces + observations + scores`；付费档 100k included、超出 $8/100k units。
- 估算本项目一轮对话约 10–20 units，50k 约合 2.5k–5k 轮/月；课程演示足够。
- 指出与原需求的冲突：最初技术栈写的是「自部署、数据不出自家服务器」；Cloud 会把 prompt/用户问题/检索片段发到 Langfuse 服务器。用户确认课程用演示数据后，拍板默认 Cloud。
- 更新 spec：默认 `LANGFUSE_BASE_URL=https://cloud.langfuse.com`；Hobby 额度/30 天窗口写入配置段；`deploy/langfuse/docker-compose.yml` 降为可选自部署方案；验收 1 改为「Cloud Hobby 建项目 + 配 env（或自部署实例）」；风险段补「Cloud 数据边界与额度」。
- 开发/面试建议：开发阶段默认 Cloud；面试演示可共享屏幕跑 Cloud，或提前起本地 compose 讲自部署；代码只换 base URL 与 key，不做两套接入。
- 本机现状：Docker 29.9.1 + `docker-compose` 5.6.0 已装，Docker daemon 未运行；Cloud 方案不需要启动 Docker。

**拒绝 / 纠偏**

- 没有在用户确认「演示数据」之前默认改成 Cloud：先指出它和「数据不出自家服务器」的原需求冲突，等用户明确拍板后才改 spec。
- 没有为了云端引入第二套接入代码：Cloud 与自部署共用 `LANGFUSE_BASE_URL` + key，compose 只是可选部署件。
- 用户中途说「先停一下，先别改」时停止继续改，先给本地/云端建议，确认后才落 spec；此前已改的三处随后已统一。

**翻车与返工**

## 2026-10-29 · 审核阶段的大模型依赖程度（方案 A）

**用户关键原话**

- 「数据飞轮这里，可以在审阅并填补回知识库时，依靠大模型吗？」
- 「那就A吧」

**Claude 关键产出**

- 给出三档：
  - A：AI 用召回片段起草 `ai_suggested_answer`，人工审核并点「通过」后才写 `approved_answer` 入库；
  - B：AI 起草 + grounded/高置信自动通过，低置信转人工；
  - C：全自动写库。
- 用户选 A。spec 更新：
  - 非目标明确「不做审核自动通过/全自动写库；人工点通过是唯一入库闸门」；
  - `QuestionNormalizer.normalize(raw_question, retrieved_chunks=None)`，有快照时要求初稿尽量引用片段，依据不足时 `grounded=False` 并标「需人工补充」，不编造政策；
  - `ai_suggested_answer` 只作初稿，`approved_answer` 存人工确认后的最终文本，两列都保留可追溯；
  - 裁决表新增第 8 条，记录 A 是用户 2026-10-29 拍板。
- 审核页仍会把召回片段、用户原话、出现次数展示给审核人，人工判断「知识库真缺」还是「有但没检到」。

**拒绝 / 纠偏**

- 没有采用 B/C：知识库是后续回答的事实来源，LLM 编造政策写进去会让系统以后「自信地答错」；B 还需要 groundedness 裁判、自动通过阈值、审计与回滚，明显超出原需求。
- 没有为了「更依赖模型」新增表/列：用现有 `ai_suggested_answer` / `approved_answer` 两列就能区分初稿与核准文本。

**翻车与返工**
