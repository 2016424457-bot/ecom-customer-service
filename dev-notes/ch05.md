## 阶段 1：Brainstorm / 定稿 Spec

- **用户关键原话**
  - 总目标：「我要用 Superpowers 模式把客服系统升级成生产级架构:Workflow 确定性编排做骨架,主力 Agent 作为骨架里的核心节点。」
  - 热身：「先不用框架,手写一遍最裸的 Agent 循环(调 LLM,有工具调用就执行并把结果喂回去,没有就收敛出答案),看清它就是个带工具的循环,再用 LangGraph 重构。」
  - 骨架：「指代消解、意图识别、按意图分流、知识检索、置信度闸、主力 Agent、日志记录。」
  - 分流：「分流规则写死在代码里」；知识类强制检索、业务数据类直接进 Agent、投诉不进 Agent、闲聊固定话术。
  - 闸：「卡在知识类检索之后、进 Agent 之前,Agent 的答复是流式吐给用户的,答完再判就晚了。」
  - 处置：「转人工、建工单是两件事,分开做,都交用户在前端自选、不后端自动执行」；「点「转人工」前端直接展示「已转接人工客服」,再蹦一句「您好,我是客服小猫,请问有什么可以帮您的」」；「点「建工单」才调第 2 章的工单工具写 tickets 表」。
  - 工作要求：「全程走 Superpowers 流程」；「产出不是可单测代码的任务……把 TDD 那步换成拿标注样例或评估集跑一遍验证」；「过程留痕……不许收尾时一次性补记」；「涉及具体库、框架、API 的用法……一律先用 Context7 MCP 查最新官方文档」；「技术选型是定死的……发现矛盾或走不通,停下来问我」。
  - 最终定稿：用户随后贴出《Ch05 设计:Workflow + Agent 混合架构(LangGraph 骨架)》与《Ch05 Workflow + Agent 混合架构 Implementation Plan》，状态「定稿(brainstorm 通过,待写实现计划)」。
- **关键产出**
  - 权威 spec：`docs/superpowers/specs/2026-07-15-ch05-workflow-agent-design.md`（用户定稿版）。
  - 适配本仓库的 plan：`docs/superpowers/plans/2026-07-15-ch05-workflow-agent.md`。
  - Context7 核对：LangGraph 1.2.16 的 `StateGraph`、`get_stream_writer`、`astream(stream_mode="custom", version="v2")`、`recursion_limit`；`astream(stream_mode=["messages","updates"])` 默认 v1 产出 `(mode, chunk)` 元组，`messages` chunk 为 `(AIMessageChunk, metadata)`，metadata 含 `langgraph_node`（本会话已用 InMemorySaver + FakeListChatModel 探针确认）。
  - 关键裁决：
    - checkpointer 按最终 spec 用 **AsyncSqliteSaver**（覆盖我早先收到的 InMemorySaver 选择）；`thread_id = str(conversation_id)`。
    - 图骨架：`coref → classify_intent → route`，四出口 knowledge / business / complaint / chitchat；knowledge 走 `forced_rag → confidence_check → agent_llm`；agent 是 `agent_llm ↔ agent_tools` 的 ReAct 环。
    - 置信度闸在 `forced_rag` 之后、`agent_llm` 之前；机械阈值 + CH04 `EvidenceChecker` 自评两道闸。
    - `create_ticket` 绑定给 Agent 但 `agent_tools` 拦截为 `suggested_actions`，不写库；按钮端点 `POST /api/actions/create-ticket` 才写 `tickets`。
    - 建工单与转人工解耦；建工单不改会话状态。
    - D7：`query_logistics` 入参改 `tracking_no`，`query_order` 增 `tracking_no`，形成真实多步依赖。
    - 前端「建工单」按 spec §6.3 弹表单（类别不预选、描述必填），不消费后端 draft；用户 plan Task 16 里的一键建单代码被 spec 覆盖。
- **独立 builder 复核（基于我早先的草稿 spec，问题已按最终 spec 裁决）**
  1. 工单类型默认推断：最终 spec §6.3 要求前端表单必选 `ticket_type`，端点 schema 直接必填，不做后端意图推断。
  2. 置信度弱分支是否给按钮：不做；最终 spec 的 `fallback_reply` 只有兜底话术 + 落池，话术不提按钮。
  3. 业务路 `query_faq` 的 citations：最终 spec 只要求 `forced_rag` 出 citations；业务路 Agent 调 `query_faq` 的引用本章不回收，记为已知限制。
  4. 检索异常语义：记 warning，`evidence_strong=False` 走弱闸兜底，不设 `state.error`，不发 SSE `error`。
- **拒绝/纠偏**
  - 用户最终选 AsyncSqliteSaver，而不是我早先问出的 InMemorySaver；按最终 spec 执行。
  - 用户 plan 的 Task 16 一键建单与 spec §6.3 表单冲突，按 spec 实现表单。
  - 用户 plan 的目录（`app/core/...`、`app/api/chat.py`、`app/static/index.html`）与本仓库不符；按 `docs/superpowers/plans/2026-07-15-ch05-workflow-agent.md` 的 Repo Mapping 映射到 `app/services/chat.py`、`app/api/routes.py`、`app/static/chat.html/js` 等，不新建平行 `app/core`。
