# CH04 · 检索质量进阶 · 开发记录

> 按阶段追记，不做事后一次性补写。每段记四样：用户关键原话、关键产出、拒绝/纠偏、翻车与返工。

## 阶段 1：Brainstorm 定稿

- **用户关键原话**
  - 初始目标：「我要用 Superpowers 模式把客服系统的检索质量做上一个台阶:混合检索加重排,再配一套评估体系。」
  - 失败场景：「检索完全未命中或命中百分之五十、但正确搭配排序不正确，且回答答非所问。」
  - 工作方式：「全程走 Superpowers 流程，技能自动触发」；「产出不是可单测代码的任务……把 TDD 那步换成拿标注样例或评估集跑一遍验证」；「前端部分是例外，用 Vibe Coding 方式直接做」；「过程留痕……不许收尾时一次性补记」；「涉及具体库、框架、API 的用法……一律先用 Context7 MCP 查最新官方文档」；「技术选型是定死的……发现矛盾或走不通，停下来问我，不要自行换方案」。
  - 关键拍板：分词用「Lite + jieba」；`faith_cases` 做「最小管理页」；Faithfulness「只跑最终策略」；评估集「48 条」。
  - 设计确认：「确认设计，进入写计划阶段」。
- **关键产出**
  - 设计文档：`docs/superpowers/specs/2026-10-22-ch04-retrieval-quality-design.md`（已确认）。
  - 独立 builder 复核：提出 5 个会逼人猜错的问题（评估驱动方式、拒答判定、`query_faq` 超时预算、两张表 DDL 原文、`done.reranked` 来源）；全部在文档中收敛，无遗留用户决策。
  - 关键决定：
    - Milvus Lite + `jieba` analyzer；BM25 function + `hybrid_search` + `RRFRanker`；dense / sparse 各 Top-50。
    - `bge-reranker-v2-m3` 走 SiliconFlow `/v1/rerank`，失败回退 hybrid 顺序。
    - Query 改写走 LLM，同义词只作用于检索侧 BM25 query。
    - 生成前自评 `useful`；不足则拒答、`low_confidence_questions.source='self_check'`。
    - 引用编号 = 相关性排名，证据按「首尾」顺序进 prompt。
    - 评估集 48 条（A/B/C/E 各 10 + F_unanswerable 8）；四策略检索指标 + 最终策略生成/裁判。
    - `faith_cases` 一题一行、`seen_count` 累计、复发退回未解决。
- **用户拒绝/纠偏**
  - 用户没有接受我最初照字面写的「内置 chinese analyzer」；在得知 Lite 不支持后，选择「Lite + jieba」而不是切 standalone Milvus。
  - 明确前端不走 brainstorm、TDD、code review，按效果描述直接改。
  - 明确技术选型不得自行替换；rerank 不可用时要停下来问。
- **翻车与返工**
  - 本机探针报 `unknown tokenizer type: 'chinese' (supported: 'standard', 'jieba')`；改为 Lite + jieba，需新增 `jieba` 依赖。这是本章第一个被强制暴露的选型矛盾。
  - `MilvusClient.search` 的参数名是 `filter=`，不是 `expr=`；第一次探针报 `search_requests_with_expr() got multiple values for keyword argument 'expr'`。`AnnSearchRequest` 才是 `expr=`，两者不能混用。
  - 沙箱拒绝访问 `api.siliconflow.cn`，`uv pip install` 的缓存目录也不可写；真实 rerank 冒烟、`jieba` 安装、建库与评估必须由用户在终端执行。
  - Builder 复核发现设计文档未包含用户给的 DDL、评估生成驱动方式、拒答判定、超时预算、`reranked` 来源；已补进设计文档。
