## 阶段 1：Brainstorm / 定稿 Spec

- **用户关键原话**
  - 「我要用 Superpowers 模式把客服系统里占位的分流器做成正式版，这是 Workflow 里最关键的节点。」
  - 功能需求 1–7：指代消解、Query 改写、Query 扩写、LLM prompt 意图识别（七类 + 其他、JSON `intent`/`confidence`、边界 few-shot）、退款/售后确定性子流程、槽位处理（缺订单号弹选择器、退款原因固定类目、需求澄清留 Agent）、前端订单卡片/退款表单。
  - 技术栈：「无新增组件，延用现有聊天上游；意图识别默认配够格的大模型，成本吃紧时再走降级路：小模型给判断和置信度，置信度低才升级大模型重判一次。」
  - 本章不做：「微调小模型 / BERT 做意图分类」「跨会话记忆」。
  - 工作要求：「全程走 Superpowers 流程，技能自动触发；产出不是可单测代码的任务（纯 Prompt、数据类），把 TDD 那步换成拿标注样例或评估集跑一遍验证；前端部分是例外，用 Vibe Coding 方式直接做。」
  - 过程留痕：「在仓库 dev-notes/ch06.md 里追记开发过程……不许收尾时一次性补记。」
  - 多轮场景：用户一时想不出具体对话，只描述「一会儿物流，一会儿问退款，一会儿又问物流了？就是一直变来变去」。
  - 追问后用户确认脚本「差不多吧」：物流（订单1001到哪了）→ 退款（那这个能退吗）→ 物流（那它什么时候到）。
  - 四个边界拍板：
    - 退款单：「真写库（推荐）」——新增 `refund_requests`，返回退款单号。
    - 「其他」：「确定性澄清（推荐）」——固定话术 + 转人工/建工单，零模型调用。
    - 验收 3 的可见位置：「评估脚本输出（推荐）」——聊天页不加内部过程区。
    - 纯政策问法：「区分后走知识检索（推荐）」——「退货政策是什么」不进子流程要订单。

- **关键产出**
  - 摸底：`coref` 是 passthrough（`app/graph/nodes.py:139`）；意图七类单标签无置信度（`app/graph/intent.py:21`）；路由写死 7→4（`app/graph/routing.py:5`）；订单只有按号查询的随机 mock（`app/tools/order.py`），没有「列出用户订单」来源；前端 `chat.js` 已有 actions/工单弹窗可复用。
  - Spec 草稿：`docs/superpowers/specs/2026-10-25-ch06-router-design.md`。
  - 设计取舍 D1–D15：八类意图 + 低置信归其他；默认大模型、可选 fast/升级；coref 一次调用出 `standalone_query` + `order_id`；扩写只用于退款/售后针对某一单的政策检索；退款检索 `content_type=policy`、售后 `content_type=manual`；订单选择器由后端 `select_order` 动作发出；pending 槽位跨轮续跑；退款判定结构化 `eligible`；售后可处理走工单、退款退货走退款表单；mock 订单确定性化；图内检索传 no-op rewriter 避免双改写。

- **拒绝/纠偏**
  - 用户否定了「一律先选单」：纯政策问题走知识检索，只有「这一单」才进退款子流程。
  - 用户否定了「其他交给主力 Agent」：怪问题不能乱调工具/幻觉，走确定性澄清。
  - 用户否定了「前端模拟退款单」：退款单必须真写库。
  - 用户否定了「聊天页折叠过程区」：验收 3 只看评估脚本输出。

- **翻车与返工**
  - 第一问「还原一段真实多轮对话」用户答不上来；改为我先给具体脚本、用户确认，避免继续空想。
  - 起草时发现「退款退货/售后一律走子流程」和「纯政策 FAQ」冲突；没有自行改需求，停下来问，用户拍板区分处理。
  - 发现现有 `query_order` 每次随机、选择器展示的数据会和后续查询对不上；决定把 mock 改成按订单号确定性生成，并列入 spec（D12）。

- **下一步**
  - 用 builder-check 子代理读 spec，按「已回答 / 小问题 / 必须问用户」三堆处理；最多带回一轮问题。
  - 用户确认 spec 后，调用 `superpowers:writing-plans` 写实现计划。

## 阶段 1.1：Builder Check（spec 评审）

- **用户关键原话**
  - 本阶段无新增用户输入；用户尚未确认 spec。
- **关键产出**
  - 独立 runner 读完 spec + 现有代码，结论：「The design is buildable; four under-specified points would force guesses that change the plan.」四个问题：
    1. `pending` 到底带什么？续跑时用哪个问题/意图？（最重要）
    2. `request_type` 怎么定退款/退货？换货怎么办？
    3. 什么时候算「订单查不到」？任意订单号都能生成数据的话，重选分支是死的。
    4. `pending_check` 靠什么识别「选单轮」？coref 超时会不会让验收 4 断掉？
  - 处理结果：四个都属于「builder 可自行决定，但会改状态/接口/测试」，按三堆归到「小问题」，直接写进 spec，不占用用户一轮：
    - D16：`pending` 固定带 `intent`、`standalone_query`、`candidate_order_ids`、`missing`；续跑恢复原意图/原问题，并追加「（订单号 X）」。
    - D17：换货/换新走售后工单，不进退款单；退货 → `request_type=退货`；其余退款 → `退款`。
    - D18：`get_order` 只对合法订单号格式生成；非法/空 → `None` → 重选，分支可达。
    - D19：续跑只认前端固定 `订单号：<id>` 或「短消息 + coref 抽号」；含其他诉求词则清 pending 正常分类；coref 超时不影响固定格式续跑。
  - Spec 已按上述四点补写；新增测试项 `test_pending.py`、`request_type` 映射、非法订单号重选。
- **拒绝/纠偏**
  - reviewer 建议的「让任意订单号都可查、同时保留查不到分支」自相矛盾；没有照单全收，改成「合法格式才生成，非法格式才 not_found」。
- **翻车与返工**
  - 无代码返工；spec 一轮补写，属于评审内正常收敛。
- **评审结论**
  - 可以进入计划阶段；无「必须问用户」的问题。
- **下一步**
  - 交给用户确认 spec；确认后调用 `superpowers:writing-plans` 写实现计划，并补记「计划评审通过」。
